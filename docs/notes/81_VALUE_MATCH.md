# MedAgentPro — התאמת שם חלקי לערך במסד (תכנון בלבד, צ׳אט 19.10, D)

**מסמך תכנון. שום קוד לא נכתב.** ההמשך של `80_GENERALITY.md`, משימה 13a: היום "Apex" לא מוצא את "Apex Polymers", כי אין התאמה חלקית ו-`=` רגיש לאותיות.

**העיקרון:** המודל מעביר את המונח של המשתמש כפי שנכתב. **הקוד הוא שמוצא את הערך**, עם ההרשאה בתוך החיפוש. המודל לא רואה ערכים מהמסד, גם לא מועמדים (NFR 21).

## מה משתנה

### הקטלוג

- **`searchable: true`** על עמודת טקסט שמותר לחפש בה לפי שם, למשל `suppliers.name` ו-`parts.description`. עמודה שלא מסומנת לא מקבלת את האופרטור החדש. כך נשאר בשליטה מה נחשף לחיפוש.
- **`max_candidates`** ברמת הקטלוג (הצעה: 5), כמה מועמדים מוצגים כשיש כמה התאמות.

### סכמה 1: אופרטור חדש

```json
{"MATCHES": {"col": "suppliers.name", "term": "Apex"}}
```

- `term` הוא **span של השאלה** (כמו `ambiguous.term` ו-`unresolved.asked`), והמהדר בודק את זה (`_check_span`). המודל לא יכול להמציא מונח.
- מותר רק על עמודה עם `searchable`. על כל עמודה אחרת: `CompileError` עם הנתיב, וניסיון משוב.

### המהדר: פתרון המונח, בקוד

לפני השליפה, ובשלושה שלבים עד ההתאמה הראשונה שמחזירה משהו:

| שלב | התנאי | למשל, "apex" |
|---|---|---|
| 1. שווה, בלי אותיות | `col = ? COLLATE NOCASE` | "APEX" |
| 2. מתחיל ב- | `col LIKE ? || '%'`, עם escape ל-`%` ו-`_` | "Apex Polymers" |
| 3. מכיל | `col LIKE '%' || ? || '%'` | "Northern Apex Ltd" |

- **ההרשאה (NFR 17) בתוך כל שלב,** בדיוק כמו בבדיקת הקיום: אותו `self.entitlement(table)`. חיפוש לא מגלה ערך שהמשתמש לא רשאי לראות, גם לא את מספר ההתאמות.
- כל שלב מוגבל ל-`max_candidates + 1` ערכים שונים, כדי לדעת אם יש יותר.
- הערכים חוזרים כפרמטרים (`?`). המונח לעולם לא נכנס לטקסט ה-SQL.

### שלוש התוצאות

| כמה נמצאו | מה קורה | מה המשתמש רואה |
|---|---|---|
| **אחד** | `MATCHES` מוחלף ב-`EQ` על הערך שנמצא, והתוכנית מהודרת מחדש (כמו A1). | התשובה, ו-Examined אומר: ‏**"supplier name 'Apex' matched Apex Polymers"**. |
| **כמה** | שום דבר לא נשלף. **בקשת בירור שהקוד בונה,** עם עד `max_candidates` מועמדים ומספר הנותרים. | ‏"'Apex' matches several supplier names: Apex Polymers, Apex Tubing, … (and 3 more). Ask again with the full name." **המועמדים מוצגים למשתמש בלבד:** הם לא נשלחים למודל, לא נכנסים להיסטוריה של השכתוב ולא לבדיקת המזהים (NFR 21, ‏NFR 27). |
| **אף אחד** | שום דבר לא נשלף. | תשובה כנה: ‏**"No supplier name matches 'Apex'."** זה ממצא, כמו "No records matched", ולא כשל. |

- **ההיסטוריה:** בבקשת בירור, השאלה הבאה ("Apex Tubing") מגיעה מהמשתמש. מזהה שהמשתמש כתב עובר את NFR 27 כרגיל. המועמדים לא נספרים כ"מוצגים" (`presented`), אלא אם הצ׳אט מחליט אחרת.
- **הרשומה:** הפתרון נרשם בשלב השליפה (המונח, השלב שהתאים, כמה נמצאו), כמו `resolved` של A1. במקרה של כמה מועמדים, הערכים עצמם לא נרשמים, כי הם נתוני חברה (K2).

## מה זה דורש

1. **שינוי בסכמה 1** (`MATCHES`), ולכן גם במה שנשלח לספק. צריך לבדוק מול מגבלות ה-structured output (‏`test_provider_enforced.py`), למרות שה-intent נשלח היום בלי `response_format`.
2. **גרסת פרומפט intent חדשה** (‏`intent_analysis_demo@10`): כלל ש-"שם של ספק או חלק שלא נכתב כמזהה" עובר כ-`MATCHES` עם המונח כפי שנכתב, ודוגמה אחת. הפרומפטים מוקפאים לדמו, אז זה רק אחרי הדמו.
3. **סבב Haiku** (משימה 1) על השאלות מ-`80_GENERALITY` (‏"Apex", "apex polymers"), ועל שאלות שבהן המונח הוא דווקא מזהה, כדי לוודא שהמודל לא מעביר מזהה ל-`MATCHES`.
4. **הערה בספר, 3.1.6** (אביתר מחליט): "a name the user writes is passed as written and resolved in code against the values the user may see; several matches return a request for clarification, built by code". אולי גם שורה במבחן 35.
5. **בדיקות, בלי מודל:** כל אחד משלושת השלבים, escape של `%` ו-`_`, ההרשאה (מתכנן שלא רואה ספק לא מקבל אותו כמועמד, גם לא בספירה), כמה מועמדים לא מגיעים לשום prompt, ו-`MATCHES` על עמודה בלי `searchable` נדחה.

## סקיצה: כינויים בקטלוג לשמות בסגנון BIRD

**הבעיה:** הסכמות דורשות `^[a-z][a-z0-9_]{0,39}$` לשם טבלה ועמודה. מסדי BIRD משתמשים באותיות גדולות, ברווחים ובשמות ארוכים (למשל `"Free Meal Count (K-12)"`).

**ההצעה:** לכל טבלה ועמודה בקטלוג יש **שם בטוח** (המפתח, לפי ה-pattern) ו-**`physical`**, השם האמיתי במסד:

```json
"frpm": {
  "physical": "frpm",
  "columns": {
    "free_meal_count_k12": {"physical": "Free Meal Count (K-12)", "type": "real", "label": "free meal count, K-12"}
  }
}
```

- **המודל רואה רק את השם הבטוח** (ב-`render_schema`), ותוכנית מדברת רק בשמות בטוחים. הסכמות לא משתנות.
- **המהדר מתרגם לשם הפיזי** בבניית ה-SQL, דרך `_q()` (שכבר עוטף כל שם במירכאות). זה המקום היחיד שמכיר את השם הפיזי.
- **Examined והכותרות** משתמשים ב-`label`, כמו היום.
- בלי `physical`, השם הבטוח הוא גם השם במסד. כך קטלוג הדמו לא משתנה.
- **פתוח:** איך מייצרים שמות בטוחים לקטלוג גדול. הצעה: כלי שמייצר אותם אוטומטית (אותיות קטנות, `_` במקום תו אחר, קיצור ל-40 תווים, ומספר כשיש התנגשות), ואדם עובר עליהם, כמו על `label`.
