# Root Cause Analysis Report

## Primary Causal Explanation

**This system is experiencing a sustained brute-force attack campaign targeting SSH and FTP services, combined with a secondary logrotate configuration issue.**

### Confidence Score: **0.92**

---

## Analysis Breakdown

### 1. **Brute-Force Attack Pattern** (Confidence: 0.95)

**Supporting Evidence:**
- **E1, E3, E4, E5**: Multiple authentication services (sshd, ftpd) showing authentication failures and unknown user attempts
- **E56**: 189 SSH authentication failures - abnormally high
- **E59**: 67 "user unknown" attempts - indicates username enumeration
- **E60**: 89 failed attempts specifically targeting root account - classic attack vector
- **E61**: 25 failed attempts targeting guest account - secondary common target
- **E58**: 15 FTP connection bursts - coordinated attack behavior
- **E27-E54**: 28 distinct source IPs from geographically diverse locations (Asia-Pacific, Europe, North America) - distributed attack pattern
- **E7-E26**: 20 anomaly events over 15 days (Jun 14-29) with clustering around 04:00-04:10 UTC - automated attack scheduling

**Attack Characteristics:**
- Distributed sources suggest botnet or coordinated attack infrastructure
- Temporal clustering (predominantly 04:00 hours) indicates automated scanning tools
- Targeting of privileged accounts (root) and common accounts (guest)
- Multi-protocol approach (SSH + FTP)

### 2. **Logrotate Operational Issue** (Confidence: 0.85)

**Supporting Evidence:**
- **E2, E6**: Logrotate exiting abnormally with error code [1]
- **E57**: 16 occurrences of logrotate failures
- **E11-E26**: Logrotate failures align with daily 04:00 timeframe - matches typical cron scheduling

**Likely Cause:**
- Logrotate failures coinciding with attack traffic suggest log file locking issues or disk I/O saturation from excessive logging
- Could also indicate permission issues or misconfigured rotation policies

---

## Recommended Actions

### **IMMEDIATE (Priority 1 - Within 1 hour)**

1. **Implement IP-based blocking** (E27-E54)
   - Block all 28 identified malicious source IPs at firewall level
   - Consider geo-blocking regions with no legitimate business need

2. **Strengthen SSH authentication** (E1, E56, E60)
   - Disable password authentication; enforce SSH key-only access
   - Disable root login via SSH (`PermitRootLogin no`)
   - Implement fail2ban or similar intrusion prevention system

3. **Secure FTP service** (E3, E58)
   - Disable FTP if not business-critical (use SFTP instead)
   - If required, implement connection rate limiting and IP whitelisting

### **SHORT-TERM (Priority 2 - Within 24 hours)**

4. **Fix logrotate configuration** (E2, E6, E57)
   - Review `/etc/logrotate.conf` and `/etc/logrotate.d/*` for errors
   - Check file permissions on log directories
   - Verify sufficient disk space and inode availability
   - Test logrotate manually: `logrotate -d /etc/logrotate.conf`

5. **Enhance monitoring** (E7-E26)
   - Set up real-time alerts for authentication failure thresholds
   - Implement SIEM correlation rules for distributed attacks
   - Monitor for privilege escalation attempts

### **MEDIUM-TERM (Priority 3 - Within 1 week)**

6. **Security hardening**
   - Change SSH to non-standard port (security through obscurity as additional layer)
   - Implement two-factor authentication for remote access
   - Remove or rename default accounts like "guest"
   - Conduct full security audit of exposed services

7. **Forensic investigation**
   - Review all authentication logs for successful logins from suspicious IPs
   - Check for unauthorized user accounts or modified system files
   - Verify no backdoors were installed during the attack window

8. **Network architecture review**
   - Implement VPN requirement for administrative access
   - Deploy intrusion detection system (IDS) if not present
   - Consider moving SSH/FTP behind bastion host
